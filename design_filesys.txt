---- SYNCHRONIZATION ----


>> A3: Explain how your code avoids a race if two processes attempt to
>> extend a file at the same time.
>>

We prevent a race by requiring a process that wishes to extend a File
to hold that inode's lock in order to do so.


>> A4: Suppose processes A and B both have file F open, both
>> positioned at end-of-file.  If A reads and B writes F at the same
>> time, A may read all, part, or none of what B writes.  However, A
>> may not read data other than what B writes, e.g. if B writes
>> nonzero data, A is not allowed to see all zeros.  Explain how your
>> code avoids this race.
>>

Whenever we begin reading data from an inode -- we truncate the read to only
go up to the file length at the read time. This way, we prevent any garbage data from being read.



>> A5: Explain how your synchronization design provides "fairness".
>> File access is "fair" if readers cannot indefinitely block writers
>> or vice versa.  That is, one or many processes reading from a file
>> cannot forever prevent another process from writing to the file, and
>> one or many processes writing to a file cannot forever prevent
>> another process from reading the file.
>>

We provide fairness by not blocking during reads and not blocking
when writing within the bounds of the file. When extending the file,
we block only for other threads that are currently attempting to extend
the file as well.




---- RATIONALE ----


>> A6: Is your file layout a multilevel indexed structure?  If so, why
>> did you choose this particular combination of direct, indirect, and
>> doubly indirect blocks?  If not, why did you choose an alternative
>> file structure, and what advantages and disadvantages does your
>> structure have, compared to a multilevel index?
>> In your explanation, include at least two reasons to support your 
>> choices.
>>
- yes, our file layout is a multilevel indexed structure with 123 direct blocks, 1 singly indirect block,
and 1 doubly indirect block
- one reason we chose this is because 123 direct blocks are good for small files by avoiding indirect block lookups
reducing disk I/O
- also the single-level indirect block (128 pointers) handles medium files efficiently, while the
doubly indirect block supports large files without requiring a third level of indirection
- this keeps the inode structure simple and limiting metadata overhead

---- ALGORITHMS ----


>> B2: Describe your code for traversing a user-specified path.  How
>> do traversals of absolute and relative paths differ?
>>
- path traversal is implemented in get_directory_filename()
- for absolute paths, we start at root via dir_open_root(). For relative paths, we start from the current working
directory via dir_reopen(cwd)
- we tokenize the path by '/' using strtok_r()
- for each token, if it's '.', we stay in current directory; if '..', we lookup parent via dir_lookup(cur_dir, "..", &parent_inode)
otherwise we lookup the token and verify it's a directory
- the last token becomes the filename. The function then ultimately returns the directory and stores the filename
- sets filename[0]='\0' if path ends with '/'


---- SYNCHRONIZATION ----


>> B3: How do you prevent races on directory entries?  For example,
>> only one of two simultaneous attempts to remove a single file
>> should succeed, as should only one of two simultaneous attempts to
>> create a file with the same name, and so on.
>>

We require the process to hold a lock to perform add, remove, or read operations on
directories. Regarding adds, if a file exists with that name already in the directory within the critical section,
we don't add it again. And with deletes we verify that the file exists in the directory
within the critical section.



>> B4: Does your implementation allow a directory to be removed if it
>> is open by a process or if it is in use as a process's current
>> working directory?  If so, what happens to that process's future
>> file system operations?  If thatâ€™s not allowed, how do you
>> prevent it?
>>
- no, our implementation prevents directory removal if the directory is open or in use
- in dir_remove() we check inode_in_use(inode) which returns true if open_cnt > 1
- if the directory is in use, removal fails
- we also prevent root removal and non-empty directory removal
- if a directory is a process's cwd, it emains open, so open_cnt > 1, preventing removal
- this ensures processes with open directory references can continue operating without accessing freed inodes

>>
- We use struct dir *cwd in the thread structure

get a copy of the parent's cwd without losing reference to it
