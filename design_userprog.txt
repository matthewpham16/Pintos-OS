>> A2: Briefly describe how you implemented argument parsing.  How do
>> you arrange for the elements of argv[] to be in the right order?
>> How do you avoid overflowing the stack page?  Is it enough to limit
>> the size of the incoming commandline?  Why or Why not?
>>

Argument parsing uses strtok_r() to tokenize the command line string on
whitespace characters. In start_process(), we parse the file_name string
and store tokens in an argv array. The MAX_ARGS constant limits to 128
arguments.

In setup_stack(), arguments are pushed onto the stack in reverse order
(argc-1 down to 0) so they appear in correct order when accessed. After
pushing argument strings, we word-align the stack pointer to a multiple of
4 bytes. Then we push pointers to each argument string in reverse order,
followed by argv pointer, argc, and a fake return address.

We must consider the total size of all arguments plus alignment padding
plus the argv pointer array so limiting commandline size alone is not enough
to prevent overflow.


---- RATIONALE ----


>> A3: Why does Pintos implement strtok_r() but not strtok()?
>>

strtok_r() is reentrant and thread-safe because it uses a caller-provided
save pointer instead of internal static state. strtok() uses static storage
to track position between calls, making it unsafe in multithreaded
environments where multiple threads might call it concurrently. Since Pintos
is a multithreaded kernel, strtok_r() prevents race conditions and data corruption.


>> A4: In Pintos, the kernel separates commands into an executable name
>> and arguments.  In Unix-like systems, the shell does this
>> separation.  Identify at least two advantages of the Unix approach.
>>

Security: The shell runs in user space with limited privileges, so bugs
in argument parsing cannot compromise the kernel. Parsing in kernel space
allows for more protection.

Flexibility: Different shells can implement different parsing behaviors
without modifying the kernel. The kernel provides a simple exec
interface accepting pre-parsed arguments.

>> B2: Describe how file descriptors are associated with open files.
>> Are file descriptors unique within the entire OS or just within a
>> single process?
>>

File descriptors are not global across the OS. Rather, they 
are unique only within a single process. Each process maintains 
its own list that maps file descriptors numbers to struct file objects. 
When a file is opened, the kernel assigns this file the next available 
descriptor number and stores a pointer to the open file in this list.

>> B3: Describe your code for accessing user data in the
>> kernel.
>>

The way user data is accessed from the kernel is by first validating every user 
provided pointer before dereferencing it. The function validate_user_pointer 
validates each pointer by checking that its not a null pointer, not a pointer to 
unmapped virtual memory, and not a pointer to kernel virtual address. If the 
pointer is invalid, the process is terminated. For strings, validate_user_string() 
walks through the entire string, validating each characters address to ensure entire 
string is valid.

>> B4: Suppose a system call causes a full page (4,096 bytes) of data
>> to be copied from user space into the kernel.  Based on your code, 
>> what is the least and the greatest possible number of inspections of 
>> the page table (e.g. calls to pagedir_get_page()) that might result?  
>> What about for a system call that only copies 2 bytes of data?  Is there 
>> room for improvement in these numbers, and how much?
>>

Each byte of user data is individually validated, so 
copying a 4 KB buffer can result in up to 4096 page table inspections 
with a min of 1 if only the first byte is checked. For a 2 byte copy it
would range from 1-2 inspections. There is room for improvement if we 
validate only the start and end address of a buffer instead. We could 
reduce worse case inspection for a 4KB buffer to about 2, improving performance.

>> B5: Any access to user program memory at a user-specified address
>> can fail due to a bad pointer value.  Such accesses must cause the
>> process to be terminated.  System calls are fraught with such
>> accesses, e.g. a "write" system call requires reading the system
>> call number from the user stack, then each of the call's three
>> arguments, then an arbitrary amount of user memory, and any of
>> these can fail at any point.  This poses a design and
>> error-handling problem: how do you best avoid obscuring the primary
>> function of code in a morass of error-handling?  Furthermore, when
>> an error is detected, how do you ensure that all temporarily
>> allocated resources (locks, buffers, etc.) are freed?  In a few
>> sentences, describe the strategy or strategies you adopted for
>> managing these issues.  Give an example.
>>

In order to avoid system call code with repetitive error handling, we 
centralized pointer validation in functions such as validate_user_pointer(), validate_user_string(), and validate_user_buffer().
These immediately terminate the process with thread_exit() if a non valid pointer is detected so individual system 
calls do not need extra error checks. This keeps the main error handling logic mostly clean. This strategy is, for 
example, handled in the sys_write case where pointers are validated once before acquiring locks or writing, 
ensuring no extra cleanup is needed if validation fails.


---- SYNCHRONIZATION ----


>> B6: Briefly describe your implementation of the "wait" system call
>> and how it interacts with process termination.
>>

The wait system call iterates through the calling thread's children
list to find the tid it is supposed to wait on. This tid is stored within
a larger struct called child. If it does not appear,
we return -1. We then block on a semaphore stored in 'child' initialized to 0. 
The child struct is initialized in the calling thread's space.
In the child process, we sema_up the child's semaphore whenever we call thread_exit. However,
before the thread actually exits, we set child->bad_exit or child->exits_gracefully
to true to indicate how the thread exited. If it exited gracefully, we also set the status
variable of the struct to the status passed by the exit() system call. We then remove the
child struct from the children list, deallocate the child struct, and return the status.

>> B7: Consider parent process P with child process C.  Explain how
>> how your code ensures synchronization and avoids race conditions
>> in each of the following cases:
>> a) when P calls wait(C) before C exits?  
>> b) when P calls wait(C) after C exits?  
>> c) when P terminates without waiting before C exits?  
>> d) when P terminates without waiting after C exits?  
>> e) Are there any special cases?
>>

a) By doing sema_down before accessing the child struct in process_wait,
and then the child process doing sema_up before it exists, we ensure that
the parent waits until the child exits to access the child's data.

b) The child's semaphore will be set to 1 when the child terminates,
so the child's exit status will be able to be viewed at anytime after C
exits w/o blocking.

c) If P terminates, the data that C provides regarding its exit will just be discarded.

d) When C terminates, the data of its exit will be there for P to view if it so chooses. 
If P ends, the data will simply be discarded.

e) If C spawns a process G and then C exits before calling wait on G, G will not return its status value to the grandparent process. 

>> B8: The "exec" system call returns -1 if loading the new executable
>> fails, so it cannot return before the new executable has completed
>> loading.  How does your code ensure this?  How is the load
>> success/failure status passed back to the thread that calls "exec"?
>>

We pass the exec load status of the child thread to a field in the parent 
thread. We accomplish this by adding a struct thread* parent in every thread
to point to its parent. In exec, we block on a semaphore stored in the calling threads struct. Once the 
child thread finishes start_process (or fails along the way) we up the semaphore to allow the exec call 
to process whether or not the exec was loaded without introducing race conditions.

---- RATIONALE ----


>> B9: What advantages or disadvantages can you see to your design
>> for file descriptors?
>>
Our file descriptor design uses a per process table implemented as a linked list of 
struct file_descriptor elements. One advantage is that file 
descriptor numbers are unique within each process so different processes can use the same fd 
values without conflict. It also makes cleanup easier when a process exits since all descriptros 
are stored in a single list. A disadvantage is that operations like read, write, or close require 
searching through the entire list which can take a lot of time if there are a lot of open files.
